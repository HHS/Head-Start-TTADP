# Plan: Automate production PR creation/update on merge to main

## Goal
On each merge to `main`, automatically create (or update, if one already exists) a `main -> production` PR, with the description, test steps, and issue list synthesized from the release's merged PRs.

## High-level flow
1. **Trigger**: `push` to `main`, plus `workflow_dispatch` (with a dry-run mode) for manual testing/debugging.
2. **Detect state**: Check for an open PR `main -> production` (`gh pr list --base production --head main --state open`). Fail the run if more than one open match exists (should never happen, but don't guess which to update).
3. **Build release-scope payload**:
   - Checkout with `fetch-depth: 0` (full history — `origin/production..origin/main` does not work with the default shallow checkout).
   - Compute first-parent commits `origin/production..origin/main`.
   - Resolve each commit to its originating PR via GitHub's "list pull requests associated with a commit" API (not by parsing squash-merge message text) — filter for merged PRs targeting `main`.
   - For commits with no resolvable PR, include normalized commit metadata rather than silently dropping them.
   - If the commit range is empty, do nothing (no-op, not an error).
   - Assemble the JSON payload matching the Credal prompt's expected shape (`mode`, `baseBranch`, `headBranch`, `releaseCommits[]`, `existingProductionPr`).
4. **Call CredalAI** (confirmed working — tested 2026-10-09):
   - `POST https://api.credal.acf.gov/api/v0/copilots/sendMessage`
   - Headers: `Authorization: Bearer $CREDAL_API_KEY_ACF`, `Content-Type: application/json`.
   - Body: `{ "agentId": "e85a3cc2-5944-11f1-aad1-9f8702339566", "message": "<JSON.stringify(releaseScopePayload)>", "userEmail": "<caller email>" }` — the release-scope payload (`mode`, `baseBranch`, `headBranch`, `releaseCommits[]`, `existingProductionPr`) goes in as a JSON-stringified string inside `message`, not as structured JSON.
   - `userEmail`: use a shared/service-account email for the CI automation rather than a personal one, if one exists — ties the automation's audit trail to an individual otherwise.
   - See [credalProductionPrPrompt.md](credalProductionPrPrompt.md) for the current agent prompt (kept in sync with what's actually configured in Credal). Add a request timeout and bounded retry.
5. **Parse and validate the response**:
   - The response body is `{ sendChatResult: { response: { message: "<JSON string>", structuredOutput: {...}, ... }, ... } }`.
   - **Parse `response.message` (JSON.parse it) as the canonical source — do not use `structuredOutput` directly.** A test call showed `structuredOutput.descriptionOfChange` missing a space after a markdown link (`...TTAHUB-5660)Add...`) that the `message` string had correctly (`...TTAHUB-5660) Add...`). The two fields aren't guaranteed to match; `message` was correct in testing, so treat it as source of truth and ignore `structuredOutput`.
   - Treat the parsed content as untrusted — schema-validate `{ title, descriptionOfChange, howToTest, issues }` (required fields present, length caps — title under ~80 chars per the updated prompt — `issues` entries match the `https://jira.acf.gov/browse/TTAHUB-####` format) before using it to touch GitHub. Fail the run rather than posting malformed content.
6. **Render PR body**:
   - The template's actual issue heading is `## Jira Issue(s)` (not `## Issue(s)`) — Credal's `issues` output is already full `https://jira.acf.gov/browse/TTAHUB-####` links; the wrapper script places that string under the real heading, so no prompt-side heading text needs to match.
   - **On create**: render the full `.github/pull_request_template.md` with the three generated sections filled in, plus the checklist defaults below.
   - **On update**: fetch the *current* PR body and replace only the three managed sections (Description of change / How to test / Jira Issue(s)) in place, using explicit HTML comment markers rather than matching on heading text where possible. Never reconstruct/overwrite the whole body from the template on update. The checklist's deterministic items are then recomputed and reapplied on top (see step 7's update) — only the non-deterministic checklist items (manual sign-offs) and any other content outside the three managed sections stay untouched.
   - **Bootstrap case (discovered 2026-10-13 testing against the real repo)**: a real open production PR (#4032) already exists, hand-written before this automation existed, with no managed-section markers. Rather than failing on every such PR and requiring a manual one-time fix, the update path tries markers first and **falls back to the same heading-based matcher `renderCreateBody` uses** when a section has no markers yet, stamping markers onto it so the PR self-upgrades to the marker-based fast path on its next update. This only throws if the heading itself is also missing (body doesn't match the template shape at all) — verified against PR #4032's real body with no mutation (`gh pr view` read + local render, no `gh pr edit`).
7. **Fill checklist defaults deterministically (script, not Credal)** — Credal explicitly declines to touch the checklist, so the script applies the same defaults already used for real production PRs (see `~/.codex/skills/ttahub-prod-pr/SKILL.md`), with one deliberate deviation from that skill (below):
   - `Linked Jira issue`, `JIRA issue status updated`, `Code is meaningfully tested`, `OHS demo complete`, `Ready to create production PR` -> `[x]`.
   - `Meets accessibility standards`, `UI review complete`, `QA review complete` -> `[n/a]` for docs/CI/infra-only releases, otherwise `[x]`.
   - `API Documentation updated`, `Boundary diagram updated` -> `[n/a]` unless the release scope materially changed API docs/system boundaries.
   - `Logical Data Model updated` -> `[x]` only if migrations/schema changes are in the release span, otherwise `[n/a]`.
   - `Architectural Decision Records written` -> `[x]` if an ADR is part of the release span, otherwise `[n/a]`.
   - **The entire "### Production Deploy" subsection, including "PR created as Draft", is never touched** — decided 2026-10-13, overriding the `ttahub-prod-pr` skill's "PR created as Draft -> `[x]`" default. Every item there reflects a real, human-performed action (draft creation sign-off, smoke test, reviewer added), not a deterministic fact about the diff, and this is enforced structurally by section boundary in `applyChecklistDefaults` (tracks entering/exiting "### Production Deploy" by heading, not just by omitting a rule for it) — so it holds even if a future template edit happens to reuse one of the covered phrases inside that section. "After merge/deploy" has no rule either and is left untouched the same way.
   - **Recomputed and reapplied on every run, create and update alike, overwriting a covered box regardless of its current state** — including one a human already changed. Decided 2026-10-13: without this, the checklist is a one-time snapshot from whenever the PR was first created, and a later merge that adds, say, a migration or UI change to the still-open PR's scope would never update "Logical Data Model updated" or "UI review complete" to match. The tradeoff is accepted deliberately: if a human unchecks one of these items for their own reason, the next merge's update will silently re-check it, since the automation can't tell "a human's deliberate override" apart from "the original deterministic default" from the checkbox state alone. This only applies to the items with a rule above — Production Deploy and After merge/deploy are always preserved regardless.
8. **Create or update**:
   - No existing PR -> `gh pr create --base production --head main --draft --title <title> --body-file <rendered>`. **Must be created as a draft** — the template requires draft creation and the `ready_for_review` transition intentionally drives Slack/Jira automation (`pr-notifications.yml`); creating it non-draft would bypass that gate and misfire notifications.
   - Existing PR -> `gh pr edit <number> --title <title> --body-file <rendered-with-managed-sections-patched>`.

## Findings from Copilot review (2026-10-13 – 2026-10-15), and fixes
Automated review on the implementation PR surfaced seven real issues across three rounds, fixed before merge:

1. **Medium — concurrent human edits could be overwritten.** The orchestrator read the existing PR body once (as part of building the release-scope payload), then wrote a body derived from that same snapshot after the Credal round-trip — a smoke-test checkbox or note a human added during that window would be silently lost. **Fix**: `tools/productionPrCLI.js` now re-fetches the live PR (`getProductionPrByNumber` in `tools/productionPr.js`, via `gh pr view --json number,title,body,state`) immediately before rendering the update, and aborts if it's no longer `OPEN`, rather than reusing the earlier snapshot. This shrinks the race window from "whole script run" to "final render + `gh pr edit` call" — it doesn't eliminate the window entirely (no compare-and-swap primitive is available via `gh`), which is an accepted residual risk given the proportionate cost of a more complex conflict-detection mechanism.
2. **Medium — Jira validation accepted missing or invented release tickets.** The schema only checked that `issues` lines were syntactically valid Jira links, never that they matched the tickets actually in the release scope — Credal could omit a ticket or substitute a different valid-looking one, and the PR notification workflow transitions whatever list it finds, making this operationally significant, not cosmetic. **Fix**: `tools/productionPrCredal.js` now extracts the expected ticket set from `releaseCommits[]` (subject/prTitle/prBody of every commit) and cross-checks Credal's `issues` output against it (`validateIssuesAgainstReleaseScope`), rejecting omissions, invented IDs, and the `TTAHUB-0` placeholder. Caught a real bug while adding this: `extractJiraKeys`'s default parameter only covered `undefined`, not the `null` that an unresolved commit's `prTitle`/`prBody` actually is — fixed to `text ?? ''`.
3. **Medium — managed markers leaked into Slack notification content.** `pr-notifications.yml`'s `extract_section` takes the raw text between headings for the Slack message, with a 600-byte truncation budget — the HTML comment marker lines (`<!-- production-pr:...:start/end -->`) were included verbatim, wasting that budget and showing raw comment syntax in Slack. **Fix**: `extract_section` now filters out any line that's a complete single-line HTML comment before truncating (`grep -vE '^[[:space:]]*<!--.*-->[[:space:]]*$' || true` — the `|| true` matters: GitHub Actions `run:` steps default to `bash -eo pipefail`, and `grep -v` exits 1 when it filters out every line, which would otherwise kill the whole step on a section that happened to become empty). This also incidentally fixes the pre-existing instructional comments in the template's Jira Issue(s) section leaking into every production PR's Slack message, not just ones this automation touches.
4. **Medium — the `push` trigger was already live with `DRY_RUN=false`.** Merging the workflow as originally written would have enabled real, automatic PR writes on every merge to `main` immediately — bypassing this very plan's own staged-rollout requirement (dry run, then explicit sign-off, before enabling push). The `workflow_dispatch` input's default doesn't protect a `push` run, since that event never reads the input at all. **Fix, then reversed by decision (2026-10-16)**: the push trigger was first removed so the workflow was dispatch only. The PR author then decided to ship the `push: branches: [main]` trigger in this same PR rather than in a follow up PR, accepting that the first real run happens on merge, against the open production PR, with no dry run in Actions beforehand. The controls that remain are the validation and draft only guarantees described above, a local dry run before merge (`DRY_RUN=true node ./tools/productionPrCLI.js`), and `gh workflow disable production-pr.yml` as an off switch that needs no PR. [ADR 0031](adr/0031-productionPrAutomation.md) records this under its consequences.
5. **Medium — `$`-token corruption risk in `setManagedSection`.** `body.replace(pattern, wrapManagedSection(...))` passed the replacement as a **string**, which makes `String.replace` treat `$&`/`` $` ``/`$'`/`$1`/`$$` as special substitution patterns rather than literal characters. Since the replacement content is LLM-generated and not guaranteed free of a literal `$`-sequence, a hit would have silently corrupted the body — `$'` in particular would duplicate everything after the match (including the real Production Deploy checklist) into the managed section. Verified in isolation: `'AAA[START]old[END]BBB'.replace(pattern, "[START]new$'literally[END]")` produces `'AAA[START]newBBBliterally[END]BBB'`, not the literal text. **Fix**: `tools/productionPrBody.js` now passes a replacer function (`() => wrapManagedSection(...)`) instead of a string, which always inserts its return value verbatim. Added a regression test with `$&`/`` $` ``/`$'`/`$1`/`$$` in the content, asserting `### Production Deploy` still appears exactly once after the update.
6. **High — generated prose fields could smuggle a fake section via an embedded `##` heading.** `descriptionOfChange` and `howToTest` had no restriction on their content, so Credal (or content it echoed from an untrusted PR body) could include e.g. `## Jira Issue(s)` plus an out-of-scope Jira link, followed by another `##` heading. Once rendered into the body, `pr-notifications.yml`'s `extract_section` — which just matches the *first* line satisfying `^## (Jira )?Issue` anywhere in the raw body, not specifically the real template section — would pick up the injected block and send its tickets to the Jira transition webhook, completely bypassing `validateIssuesAgainstReleaseScope`'s cross-check on the real, separate `issues` field. Verified by constructing exactly this payload against `validateProductionPrContent` before the fix: it was accepted. **Fix**: `tools/productionPrCredal.js` adds a custom Joi validator (`rejectEmbeddedHeading`, pattern `/^##[^#]/m`) on both `descriptionOfChange` and `howToTest`, rejecting any line starting with exactly `##` (an H3 `###` is fine — confirmed `pr-notifications.yml`'s `^## ` match can't fire on it). `issues` itself doesn't need this check: its existing per-line Jira-link format validator already can't be satisfied by a heading line.
7. **Medium — CRLF line endings silently defeated checklist-default matching.** `applyChecklistDefaults`'s checkbox regex ended in `(.*)$`; since JS's `.` never matches `\r` and there's no `m` flag, a line with a trailing `\r` (i.e. every line except the body's last, under CRLF) failed to match at all, leaving that checklist item completely untouched. This isn't a theoretical edge case — **the real PR #4032 body fetched earlier in this plan uses CRLF line endings**, meaning the bug had been live, undetected, the entire time, because every unit-test fixture in this plan was built with plain `\n`. Reproduced directly: applying defaults to a 2-line CRLF checklist left the non-last line unchecked while the last line correctly got checked. **Fix**: the regex now ends in `(.*)(\r?)$`, capturing and re-appending an optional trailing `\r` so both line-ending styles work, with a regression test running the full checklist (including the Production Deploy exclusion) against a CRLF-joined body.

## Never touch "### Production Deploy" (explicit requirement, 2026-10-13)
Beyond the `ttahub-prod-pr` skill's default of auto-checking "PR created as Draft", the decision here is that **no item in "### Production Deploy" is ever touched by this automation**, full stop — every item there is a real human sign-off (draft creation confirmed, smoke test run, reviewer added), not a fact derivable from the diff. This is enforced structurally in `applyChecklistDefaults` by tracking section boundaries (entering on the `### Production Deploy` heading, exiting on the next heading of any level) rather than relying on no `CHECKLIST_RULES` entry happening to match text in that section — see step 7 above and `tools/productionPrChecklist.js`.

## Why not the `ttahub-pr` skill, and how `ttahub-prod-pr` factors in
The (Claude Code) `ttahub-pr` skill is scoped to interactive, single feature-branch PRs — it pulls a Jira ticket from the branch name and fills the template from one diff, not a multi-PR release summary.

There's also a `ttahub-prod-pr` skill (Codex CLI, `~/.codex/skills/ttahub-prod-pr/SKILL.md`) that already encodes the real production-PR pattern this automation targets: draft-only, derive from `origin/production..origin/main`, Jira-linked flat bullets, and — notably — a **fixed "How to test" string** and **deterministic checklist defaults**, rather than LLM-generated versions of either. That skill isn't invocable from this session (different tool), but its rules were folded in directly:
- How to test and checklist handling in this plan now match that skill's deterministic approach (steps 6 and 7 above), rather than what the original Credal prompt draft asked for (freeform generated test steps, which risked implying validation that wasn't actually described in the source PRs).
- Title/description-bullet generation is the one piece that still needs an LLM — theme-grouping across many unrelated PRs into a short title, and condensing each PR's body into one release-note line, are both summarization judgment calls that rule-based matching can't do well. Credal (now connected) handles exactly that, with no update needed to its role in the design.

## Components
- **Workflow**: [.github/workflows/production-pr.yml](../.github/workflows/production-pr.yml) — runs on every push to `main` (always for real) and on `workflow_dispatch`, which has a `dry_run` boolean input that defaults to `true`. See Copilot finding #4 below for why the push trigger is enabled from the first merge. Permissions (`contents: read`, `pull-requests: write`), concurrency group (`production-pr`, `cancel-in-progress: false`). Checks out with `fetch-depth: 0`, sets up Node via `.nvmrc`, runs `yarn install --production --frozen-lockfile` (only `joi` is needed from `node_modules`), then runs the orchestrator.
- **Scripts** (plain JS in top-level `tools/`, not `src/tools/*.ts` — see the MVP sequencing entries below for why):
  - `tools/productionPr.js` — commit-range + associated-PR resolution (via `gh api`, not `@octokit/rest` — no new npm dependency needed), existing-PR detection, payload assembly, `getChangedFiles`, and the `gh pr create --draft`/`gh pr edit` wrappers (`--body-file`, not a shell argument).
  - `tools/productionPrChecklist.js` — deterministic checklist-default logic.
  - `tools/productionPrCredal.js` — the Credal API call, response parsing/validation, retry logic.
  - `tools/productionPrBody.js` — template rendering (create) and managed-section patching with heading-based fallback (update).
  - `tools/productionPrCLI.js` — the orchestrator: builds the payload, no-ops on an empty range, calls Credal, renders the body (create or update path), and calls `gh` unless `DRY_RUN=true` (in which case it logs what it would do). Not unit tested directly, matching this repo's convention for I/O-wrapper entry points (e.g. `tools/releaseInventory.js`) — its building blocks are each tested in isolation instead.
- **Secrets/variables**: `CREDAL_API_KEY_ACF` (secret, already connected), `PRODUCTION_PR_CREDAL_USER_EMAIL` (repo/org variable — **still needs to be created**; should be a shared/service-account email, not a personal one, per the open question below).
- **Also touched**: [.github/workflows/pr-notifications.yml](../.github/workflows/pr-notifications.yml) — `extract_section` strips managed-marker (and other) HTML comment lines before truncating for Slack (see Copilot findings below).
- **Tests**: `tools/productionPr.test.js`, `tools/productionPrChecklist.test.js`, `tools/productionPrCredal.test.js`, `tools/productionPrBody.test.js` — 84 tests covering commit normalization, checklist-default logic (including the hard Production Deploy exclusion and CRLF bodies), response validation/retry, Jira cross-scope validation, embedded-heading rejection, and repeated/idempotent body updates (including against a real legacy PR body shape and `$`-token content). All passing, lint clean.

2. ~~**Repo/token permissions**~~ — resolved (checked 2026-10-09):
   - `gh api repos/HHS/Head-Start-TTADP/actions/permissions/workflow` returns `"can_approve_pull_request_reviews": true` (the API name for "Allow GitHub Actions to create and approve pull requests"), so default `GITHUB_TOKEN` can create/edit PRs in this repo. No PAT needed.
   - Production deploys run on CircleCI, triggered by a push to `production` (the merge itself) — per `docs/guides/infrastructure.md` — not by any GitHub Actions `pull_request` workflow, so `GITHUB_TOKEN`-authored PRs not firing `pull_request` events is a non-issue for deploy.
   - The one workflow keyed on a production-PR `pull_request` event is `pr-notifications.yml` (`types: [ready_for_review]`). That event fires when a human clicks "Ready for review" in the UI (their own session, not `GITHUB_TOKEN`), so it's unaffected by how the PR was originally created. No other workflow in this repo acts on a production PR's `opened`/`synchronize` events (they all explicitly skip `base.ref == 'production'`).
   - Workflow permissions needed: `contents: read`, `pull-requests: write` — standard default-token scopes, as already specified under Components.
3. ~~**Failure behavior**~~ — resolved: **fail loudly**. If the Credal call errors, times out, or returns invalid/malformed output, the workflow run fails and no PR is created or updated — never post a degraded/placeholder body to a real production PR. A human notices the failed run and re-triggers or investigates; this is preferred over silently degrading quality in a document people rely on for production release review.

## Explicit state handling to define
- Zero commits in range -> no-op.
- Multiple open `main -> production` PRs -> fail (ambiguous, don't guess).
- Force-pushes to `main` -> re-run naturally on next push; no special handling needed beyond idempotent update logic.
- Closed-but-unmerged production PR -> treat as "no existing PR", create a new one.
- Malformed/unparseable current PR body on update -> the heading-based fallback (see the Bootstrap case above) handles the common "predates this automation" case; only a body missing the heading entirely still fails rather than corrupting it.
- Credal call fails/times out -> fail the run, no partial PR content.
